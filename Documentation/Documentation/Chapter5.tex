\chapter{Implémentation du système}

\section{Présentation générale du backend}

\noindent Le backend du système URGmetEO constitue une composante essentielle de l’architecture globale de la plateforme. Il est chargé du traitement des données, de la gestion des échanges avec les services externes ainsi que de la réception et du traitement des requêtes provenant de l’application mobile.\\

\noindent En effet, cette couche joue un rôle central dans le fonctionnement du système. D’une part, elle permet de récupérer les données météorologiques issues du serveur distant de l’institution URGEO. D’autre part, elle assure le traitement et la structuration de ces données afin de les rendre exploitables par l’application mobile.

\noindent Par ailleurs, le backend prend en charge plusieurs fonctionnalités importantes, notamment la gestion des alertes météorologiques, des prévisions ainsi que de l’historique des observations. Il assure également la communication avec le module IoT basé sur un microcontrôleur ESP32, utilisé pour le système d’alerte visuelle.

\noindent Enfin, le backend expose un ensemble d’interfaces de programmation sous forme d’API REST. Ces interfaces permettent à l’application mobile d’accéder de manière simple et sécurisée aux différentes ressources du système.


\section{Technologies utilisées}


\noindent Le backend du projet URGmetEO a été développé en s’appuyant sur un ensemble de technologies modernes, adaptées à la conception d’applications web performantes et évolutives . L’ensemble de ces technologies permet de mettre en place une architecture à la fois flexible, structurée et facilement maintenable.\\

\noindent Le langage principal utilisé est JavaScript, à travers l’environnement d’exécution Node.js, qui permet de développer des applications côté serveur de manière efficace. Afin de faciliter la création des API REST, le framework Express.js a été utilisé, offrant une structure simple et flexible pour la gestion des routes et des requêtes HTTP.\\

\noindent L’implémentation du backend a été réalisée à l’aide de l’environnement de développement Visual Studio Code, qui fournit des outils adaptés à la programmation et au débogage.\\

\noindent Par ailleurs, l’outil Swagger a été intégré afin de documenter les différentes routes de l’API et de faciliter leur visualisation. Enfin, Postman a été utilisé durant la phase de développement pour tester les différents endpoints et vérifier le bon fonctionnement des échanges entre le client et le serveur.\\

\noindent L’ensemble de ces technologies permet de mettre en place une architecture à la fois flexible, structurée et facilement maintenable.

\section{Architecture du backend}

\noindent Le backend du projet URGmetEO repose sur une architecture modulaire inspirée du modèle MVC (Model -- View -- Controller), adaptée aux applications basées sur des API REST. Cette approche permet d’organiser le code de manière claire tout en facilitant son évolution.

\noindent L’organisation du backend s’appuie principalement sur les composants suivants :

\begin{itemize}
\item Model
\item Route
\item Controller
\item Service
\end{itemize}

\noindent Chacun de ces éléments joue un rôle spécifique dans le fonctionnement du système. En complément, d’autres dossiers sont utilisés afin de structurer certaines fonctionnalités et d’améliorer l’organisation globale du projet. Cette architecture présente plusieurs avantages. Elle permet tout d’abord de séparer clairement les responsabilités entre les différents composants. Ensuite, elle facilite la maintenance et l’évolution du système. Enfin, elle rend le code plus lisible et plus structuré.


\section{Organisation du backend}


\noindent Le backend est organisé en plusieurs dossiers, chacun ayant une responsabilité bien définie.\\ 

\noindent \textbf{Dossier Model}  

\noindent Le dossier Model contient les modèles de données utilisés dans l’application. Ces modèles définissent la structure des objets manipulés, tels que :
\begin{itemize}
\item les données météorologiques ;
\item les stations météo ;
\item les alertes ;
\item les utilisateurs.
\end{itemize}

\noindent Ils servent également d’interface avec la base de données MongoDB.\\

\noindent \textbf{Dossier Route}  

\noindent Le dossier Route regroupe les différentes routes de l’API. Chaque route correspond à un endpoint accessible via HTTP, permettant à l’application mobile de communiquer avec le backend.

\noindent Les routes définissent notamment :
\begin{itemize}
\item l’URL ;
\item la méthode HTTP (GET, POST) ;
\item le contrôleur associé.\\
\end{itemize}


\noindent \textbf{Dossier Controller}  

\noindent Les Controllers assurent le traitement des requêtes provenant des routes. Ils reçoivent les requêtes, valident les données, appellent les services nécessaires et retournent la réponse au client. Ils jouent ainsi un rôle d’intermédiaire entre les routes et la logique métier.\\


\noindent \textbf{Dossier Service}  

\noindent Le dossier Service contient la logique métier de l’application. Il regroupe les traitements nécessaires aux données, tels que :
\begin{itemize}
\item la récupération des données météorologiques ;
\item le traitement des alertes météo ;
\item la gestion des historiques ;
\item la communication avec les stations météo.
\end{itemize}

\noindent Cette organisation permet d’éviter d’intégrer la logique métier directement dans les contrôleurs, ce qui rend le code plus clair et plus maintenable.\\

\noindent \textbf{Dossiers complémentaires}  

\noindent En plus des composants principaux, le backend comprend d’autres dossiers destinés à organiser certaines fonctionnalités techniques :
\begin{itemize}
\item \textbf{Utils} : contient des fonctions utilitaires réutilisables dans différentes parties du projet ;
\item \textbf{Scripts} : contient des scripts utilisés pour des tâches spécifiques, comme l’initialisation ou le traitement automatisé des données.
\end{itemize}

\noindent Le fichier principal \texttt{server.js} constitue le point d’entrée du serveur. Il est responsable de :
\begin{itemize}
\item l’initialisation de l’application Express ;
\item la configuration des routes ;
\item le démarrage du serveur backend.
\end{itemize}


\section{Tests des API}

\noindent Une fois le serveur backend lancé, les différentes routes de l’API peuvent être testées à l’aide d’outils spécialisés. Dans le cadre du projet, deux outils principaux ont été utilisés: Postman et Swagger.

\noindent \textbf{Postman}  

\noindent Postman permet de tester les endpoints en envoyant des requêtes HTTP vers le serveur backend. Il permet notamment de :
\begin{itemize}
\item tester les méthodes GET, POST, PUT et DELETE ;
\item vérifier les réponses retournées par le serveur ;
\item simuler différentes requêtes provenant de l’application mobile.
\end{itemize}

\noindent \textbf{Swagger}  

\noindent Le projet intègre également Swagger, un outil de documentation interactive des API. Il permet de :
\begin{itemize}
\item visualiser l’ensemble des endpoints disponibles ;
\item consulter les paramètres requis pour chaque requête ;
\item tester directement les routes depuis une interface web.
\end{itemize}





\section{Endpoints principaux de l’API}

\noindent Le backend URGmetEO expose plusieurs endpoints permettant de gérer les différentes fonctionnalités de l’application mobile. Les principales catégories sont les suivantes :\\

\noindent \textbf{API d’authentification}  

\noindent Ces endpoints permettent de gérer l’authentification des utilisateurs ainsi que la sécurisation de l’accès aux ressources du système.

\noindent Fonctionnalités principales :
\begin{itemize}
\item connexion des utilisateurs ;
\item gestion des sessions.\\
\end{itemize}

\noindent \textbf{API des alertes météorologiques}  

\noindent Ces endpoints permettent de récupérer et de gérer les alertes météorologiques détectées par le système.

\noindent Ils sont utilisés pour :
\begin{itemize}
\item afficher les alertes dans l’application mobile ;
\item déclencher des notifications en cas de conditions météorologiques critiques.\\
\end{itemize}

\noindent \textbf{API des prévisions météorologiques}  

\noindent Ces endpoints fournissent les prévisions météorologiques sur plusieurs jours.

\noindent Ils permettent à l’application mobile d’afficher :
\begin{itemize}
\item la température ;
\item la pression ;
\item l’humidité ;
\item la vitesse du vent.\\
\end{itemize}

\noindent \textbf{API des historiques}  

\noindent Ces endpoints permettent d’accéder aux données météorologiques historiques collectées par les stations.

\noindent Ces données peuvent être utilisées pour :
\begin{itemize}
\item l’analyse des tendances météorologiques ;
\item l’affichage de graphiques dans l’application mobile.\\
\end{itemize}

\noindent \textbf{API de géolocalisation}  

\noindent Ces endpoints permettent d’obtenir les informations météorologiques correspondant à la position géographique de l’utilisateur, à partir des coordonnées GPS envoyées par l’application mobile.\\

\noindent \textbf{API des stations météorologiques}  

\noindent Ces endpoints permettent de gérer les stations météorologiques installées dans différentes zones.

\noindent Ils permettent notamment :
\begin{itemize}
\item de récupérer la liste des stations disponibles ;
\item d’obtenir les données météorologiques associées à chaque station.\\
\end{itemize}


\section{Exemple d’implémentation d’un endpoint}

\noindent Afin d’illustrer le fonctionnement du backend du système URGmetEO, cette section présente un exemple d’implémentation d’un endpoint permettant de récupérer les alertes météorologiques.

\noindent Le backend du projet repose sur une architecture en plusieurs couches, composée principalement de Routes, Controllers, Services et Models. Cette organisation permet de séparer les responsabilités et de faciliter la maintenance du code.

\noindent Lorsqu’une requête est envoyée par l’application mobile, elle suit généralement le processus suivant :
\begin{enumerate}
\item L’application mobile envoie une requête HTTP vers une route de l’API ;
\item La route redirige la requête vers le contrôleur correspondant ;
\item Le contrôleur appelle un service chargé de traiter les données ;
\item Le service applique la logique métier et récupère les informations nécessaires ;
\item La réponse est ensuite renvoyée au client sous forme de données JSON.
\end{enumerate}

\noindent Cette organisation permet de structurer le code de manière claire et de rendre le système plus évolutif.

\subsection{Définition de la route}

\noindent Les routes permettent de définir les différentes adresses (endpoints) par lesquelles les clients accèdent aux fonctionnalités de l’API.

\noindent Dans le fichier \texttt{server.js}, les routes liées aux alertes sont enregistrées comme suit :

\begin{verbatim}
const alertRoutes = require('./routes/alerts');
app.use('/api/alerts', alertRoutes);
\end{verbatim}

\noindent Ainsi, toutes les requêtes adressées à \texttt{/api/alerts} sont redirigées vers le fichier \texttt{alerts.js} situé dans le dossier routes.

\noindent Dans ce fichier, une route de type GET est utilisée pour récupérer la liste des alertes météorologiques.

\subsection{Implémentation du Controller}

\noindent Le contrôleur reçoit la requête provenant de la route et coordonne son traitement.

\begin{itemize}
\item recevoir la requête HTTP ;
\item appeler le service correspondant ;
\item gérer les éventuelles erreurs ;
\item retourner la réponse au client.
\end{itemize}

\subsection{Implémentation du Service}

\noindent Le service contient la logique métier de l’application et permet de détecter des situations à risque.

\begin{itemize}
\item température très élevée ;
\item vent violent ;
\item pression atmosphérique anormalement basse ;
\item fortes précipitations.
\end{itemize}

\subsection{Réponse de l’API}

\noindent Une fois la requête traitée, le backend renvoie une réponse au format JSON.

\begin{verbatim}
{
  "success": true,
  "data": [
    {
      "type": "CANICULE",
      "message": "Température élevée (36°C) détectée",
      "level": "high"
    }
  ]
}
\end{verbatim}
